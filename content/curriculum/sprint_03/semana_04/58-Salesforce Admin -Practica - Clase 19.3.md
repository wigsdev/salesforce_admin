TIPS FLOWS

El Concepto: "Si no lo buscas, no existe"

El Síntoma: El Flow hace su trabajo en las pruebas, pero falla o ignora datos en producción.
La Causa: Diseñar pensando en el registro que tengo delante, no en la base de datos completa.
La Realidad de Salesforce: Los procesos no son individuales; Salesforce procesa en lotes (batches).
El Mantra: "Si no lo buscas con un Get Records, el Flow está ciego".
vamos a ver la segunda parte de modelado de datos… 



El Motor del Flow: Get Records

Sin búsqueda no hay mapeo masivo
¿Para qué sirve?: Es el "archivador". Si quieres tocar registros que no son el que disparó el flow, tienes que abrirlos.
Configuración Crítica: * ❌ Only the first record: Limita el Flow a un solo resultado (Mapeo pobre).
✅ All records: Crea una Colección (Mapeo escalable).
Filtros Inteligentes: El filtrado se hace en el Get Records (Base de Datos), no después con Decisiones (Memoria).
vamos a ver la segunda parte de modelado de datos… 



Anatomía de un Flow Escalable

El patrón que nunca falla: "Buscar - Recorrer - Guardar"
Get Records (All): Traemos la "bolsa" de registros.
Loop: Sacamos uno por uno para inspeccionarlos.
Assignment: Cambiamos los valores y metemos el registro en una nueva bolsa de salida.
Update Records (FUERA del Loop): Vaciamos la bolsa de salida en la base de datos de un solo golpe.
vamos a ver la segunda parte de modelado de datos… 



Errores Fatales (Anti-Patrones)

Lo que mata el rendimiento en Salesforce
Elementos Rosas en Bucles: NUNCA pongas un Get Records o Update Records dentro de un Loop.
Consecuencia: Error de "Too many SOQL queries / DML statements".
Hardcoding de IDs: Usar 0015... en los filtros.
Solución: Usar variables de referencia o nombres de API.
Falta de Fault Paths: Si el mapeo masivo falla, el Flow muere en silencio. ¡Usa rutas de error!
vamos a ver la segunda parte de modelado de datos… 



Tips específicos por tipo de Flow

Record-Triggered Flows (El motor automático)
Antes de guardar (Fast Field Updates): Si solo vas a actualizar campos del mismo registro que disparó el flow, usa siempre esta opción. Es 10 veces más rápida y no dispara recursividad innecesaria.
Después de guardar (Actions & Related Records): Úsalo solo si necesitas actualizar registros relacionados o enviar emails.
Entry Conditions: Nunca dejes un flow "abierto". Define condiciones de entrada granulares para que el flow solo se ejecute cuando sea estrictamente necesario.
vamos a ver la segunda parte de modelado de datos… 



Tips específicos por tipo de Flow

Schedule-Triggered Flows (El procesamiento masivo)
El objeto es la clave: Al configurar el Flow programado, selecciona el Objeto. Salesforce automáticamente "fragmentará" el trabajo.
No hagas un Get Records de todos los registros: Si seleccionas el objeto en la configuración inicial, el Flow se ejecuta una vez por cada registro que cumpla el criterio, actuando como un loop automático y escalable.
vamos a ver la segunda parte de modelado de datos… 



Tips específicos por tipo de Flow

Screen Flows (La experiencia de usuario)
Validación de entrada: No confíes en el usuario. Usa las validaciones de los componentes de pantalla para asegurar que los datos llegan limpios al motor del flow.
Confirmación final: Siempre muestra una pantalla de éxito o resumen al final. Un flow que se cierra sin avisar genera incertidumbre.

Hardcoding IDs
Los IDs cambian entre Sandbox y Producción.
Usa nombres de API o busca el registro por un campo único (DeveloperName).
No usar el "Triggering Record"
Crear un "Get Records" para buscar el registro que ya disparó el flow.
Usa la variable global {!$Record}.
Ignorar los Fault Paths
Si algo falla, el usuario ve un error genérico "unhandled exception".
Crea rutas de error (Fault lines) para manejar excepciones o enviar correos de alerta.
Loops infinitos
Modificar el registro que dispara el flow de forma que se vuelva a disparar a sí mismo.
Usar condiciones de entrada como "Only when a record is updated to meet the condition requirements".
